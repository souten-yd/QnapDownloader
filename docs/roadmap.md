# QnapDownloader ロードマップ（2026-11-02 ブラッシュアップ版）

**位置づけ:** 以後の開発順序の正本。`docs/implementation-plan.md` の PR-1…PR-5 表と `docs/embedded-jd2-architecture.md` の Engine-0…7 は背景資料として残し、本書と矛盾する場合は本書を優先する。安全上の禁止事項（`DEVELOPMENT_WORKFLOW.md`・`embedded-jd2-architecture.md` の Do NOT）は一切緩めない。

## 1. 前回案からの主な変更点

| 項目 | 前回案 | ブラッシュアップ後 | 理由 |
|---|---|---|---|
| 最初に着手するもの | ローカルブリッジ | **ブラウザ型Web管理画面（M0）** | ブリッジは実機・JD2配布許諾がブロッカーで、この環境では検証できない。UIはNASなしで検証でき、毎日の使い勝手を即改善できる |
| ローカルブリッジの認証 | 「認証済みQnapDownloaderだけがアクセス」 | **リスナー所有者検証方式**（後述 §3） | JD2旧RemoteAPI（3128）は認証機能を持たず、MyJD Direct Connection（3129）はMyJDアカウント必須。認証を「付ける」のではなく「到達できる者を限定し、毎回確認する」設計が現実的 |
| ディスクI/O診断 | Hubの`/proc/self/io`のみ | **HDDスピンアップ計測**（`/proc/diskstats` の差分を利用者操作時だけRAM上で取る）を追加 | 「アイドル中にHDDを起こさない」という目標を直接測れる指標にする |
| JD2ログのRAM化 | Docker構成次第 | 内蔵エンジン時のみ。外部Dockerは**変更手順の提示のみ** | 既存コンテナを無断変更しない原則を維持 |
| 進捗の取得 | 手動更新のみ | **表示中のみの任意自動更新**（既定OFF・画面非表示で停止） | 使い勝手と、バックグラウンドポーリング禁止の両立 |

## 2. マイルストーン

各マイルストーンは原則1PR（大きい場合は分割）。PR番号ではなく計画上の識別子。

### M0 — ブラウザ型Web管理画面（v0.1.9〜0.1.10、完了）
- 一般的なWebブラウザ（Chrome/Safari）と同じ操作感：タブ列・アドレスバー（オムニボックス）・戻る/進む/再読み込み・ブックマークバー・新しいタブページ。
- **管理画面は「固定タブ」、Web閲覧は「通常タブ」**に分離。固定タブは閉じられず左端に並び、通常タブは閉じる・並べ替え不要の最大6枚。スマートフォンではSafari型の下部ツールバー＋タブ一覧に切り替える。詳細: `docs/browser-shell-ui.md`。
- バックエンドAPI・DB・セキュリティ境界は変更しない（フロントエンドのみ）。iframe sandbox方針（allow-same-origin禁止等）を維持し、テストで静的に検証する。
- 受入れ: verify.sh合格、静的セキュリティ検査、ヘッドレスブラウザでのPC/iPhone幅の表示確認。QPKGビルド・実機確認はQDK環境で別途（未実施なら未実施と明記）。

### M1 — ローカル接続ブリッジ + エンジン初期設定（v0.1.11で実装、実機検証は未実施）
> **更新（2026-11-02）:** MyJDownloader連携は削除。M1は `docs/engine-setup.md` の「初期設定ボタンでJava/JD2を公式URLから取得・検証して導入し、Hubが起動・監視する」方式に拡張された（`engine_components.py` / `engine_supervisor.py` / `jd2_local.py`）。以下は当初計画（履歴）。
- 目的: MyJDアカウントなしで、同一NAS上のJD2から状態を読む（履歴。MyJD連携自体はv0.1.11で削除）。
- 方式: §3 の「リスナー所有者検証」付きで旧RemoteAPIを**読み取り系メソッドの許可リストだけ**呼ぶアダプタ `jd2_local.py`。既存 `jd2_downloads.py` の正規化を再利用し、UIはMyJD経由と同じ表示モデル。
- 外部Docker JD2の場合、3128をホストへ公開しない構成（Hubが同じネットワーク名前空間に入る等）の手順をドキュメントで提示するだけで、コンテナは変更しない。
- 受入れ: TS-253Beで、(a) LAN他端末から3128に届かない、(b) 0.0.0.0待受や別PIDの待受を検知したら接続拒否、(c) 読み取り結果がJD2画面と一致。

### M1.5 — JD2のコンテナ化（v0.1.15で実装、実機検証は未実施）
- `docs/container-runtime.md` §2〜3 の実装。Container Stationが使える場合、JD2を Hub 専用コンテナ `qnapdl-jd2`（非root・読み取り専用・メモリ1GB・ポート非公開・専用ブリッジネットワーク）で動かす。`container_runtime.py`（固定操作のみのDocker CLIラッパ）、`engine_supervisor.py`（mode: container / native）、`jd2_local.py`（コンテナIPへ接続、毎回inspect検証）。
- ネイティブ方式はContainer Stationが無い環境のフォールバックとして残す。既存のネイティブ導入は「コンテナへ移行」で同じ `engine/jd2` のデータのまま移せる。
- リモートブラウザ（`container-runtime.md` §4）は v0.1.16 の予定（未実装）。
- 受入れ（実機で未確認）: コンテナ起動とJD2初回アップデートの完了、LANから3128に届かないこと、`/jd2/logs` tmpfsでJD2が動くこと、`/tmp` の noexec で問題が出ないこと、保存先の書込権限（uid 1000）。

### M2 — ダウンロード操作（開始/一時停止/再開/削除）
- 既存方針どおり、対象revision照合・二段階確認・readback・通信不明時は再試行しない。削除はファイル削除OFFが既定。
- Hub内に**RAMのみの状態キャッシュ**（最大N件・TTL数秒）を置き、複数端末から開いても JD2 への問い合わせを1本に束ねる。ディスクへは書かない。

### M3 — 低I/O計測と最適化
- `GET /api/diagnostics/disk-activity?seconds=60..300`：管理者が押した時だけ、`/proc/diskstats` の対象HDDの読書セクタ・I/O回数を開始/終了で差分取得（結果は保存しない）。Hub・JD2(Java)・その他を `/proc/<pid>/io` で分離表示（読めない場合は「権限不足」と明示）。
- 計測結果に基づき、内蔵JD2のログ出力先を上限付きtmpfsへ（swap・OOMガード付き、失敗時は永続ログへフォールバックせず停止して通知）。設定・アカウント・キュー・未完了DLは永続領域のまま。
- Hub SQLite は WAL + synchronous=FULL を維持。表示・閲覧系の操作でDB書込が起きないことをテストで保証。

### M4 以降 — 内蔵JD2エンジン
`docs/embedded-jd2-architecture.md` の Engine-0〜7 を、M1の結果（ブリッジ方式の確定）を前提に進める。JD2配布許諾の確認が前提ゲートである点は変わらない。

## 3. ローカルブリッジの認証設計（ブラッシュアップ）

調査結果:
- JD2の旧RemoteAPI（deprecated API、既定3128）は `cfg/org.jdownloader.api.RemoteAPIConfig.json` の `deprecatedapienabled` で有効化するローカルAPIで、資格情報による認証の仕組みは文書化されていない。
- （履歴）MyJD の Direct Connection（3129）はローカルLAN直結でも MyJD アカウントが前提だった。
- したがって「MyJD不要」かつ「認証付き」をJD2側だけで満たす手段はなく、リスナー所有者検証方式を採用した（v0.1.11で実装）。

採用方式（リスナー所有者検証）:
1. JD2は `127.0.0.1` のみで待ち受ける（内蔵エンジンはHubが起動引数・設定で強制。外部Dockerはホストへ公開しない構成のみ対応）。
2. Hubは**接続のたびに** `/proc/net/tcp`（と`tcp6`）を読み、3128の待受アドレスが `127.0.0.1` だけであること、そのソケットinodeを保有するPIDが Hub が起動・記録したJD2プロセス（実行ファイル・cmdline・開始時刻で照合）であることを確認する。不一致なら接続しない。
3. 呼び出せるメソッドは Hub 内の固定許可リストのみ（任意メソッド名の中継は禁止）。ブラウザからJD2へ直接届く経路は作らない。
4. （ネイティブ方式のみ。コンテナ方式は `docs/engine-setup.md` の「コンテナ方式」参照）残余リスク（同一ホスト上のroot権限プロセスは到達可能）を受入れ条件に明記。QNAP上のホストプロセスは管理者権限相当であり、Hub自身と同じ信頼境界とみなす。コンテナ（ブリッジネットワーク）は別ネットワーク名前空間のため `127.0.0.1` に届かないことを実機で確認する。

## 4. 変わらない前提
- 自動開始・自動解凍・自動削除・パッケージ別フォルダはOFF。Cloudflare等の回避はしない。
- Hub QPKG更新とJD2更新は独立。
- 設定・キュー・アカウントはRAMだけに置かない（停電で失われるため）。tmpfsは上限付き・swapの影響を考慮。
- 実機・ビルド・リリースを実施していないものは「未実施」と書く。
